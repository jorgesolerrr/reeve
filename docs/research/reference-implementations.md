# Reference implementations: what the code of Emdash, vibe-kanban, and sortie actually teaches

**Research date:** 2026-07-26
**Question:** ADR-0002 committed reeve to *studying* Emdash, vibe-kanban, and sortie instead of forking them. This is that study — at the code level, not the product level ([competitive-landscape.md](./competitive-landscape.md) already covered the products). What shapes should reeve's LLD copy, and what mistakes are sitting in these codebases as warnings?
**Method:** Full clones read locally. Citations are `repo@path` with line numbers where they matter. Revisions read: vibe-kanban `4deb7ec` (v0.1.44, 2026-04-24 — the final Bloop-era release), emdash `5ace464` (2026-07-25), sortie `fcd496a` (2026-07-20). GitHub issues quoted via `gh`.
**Companion notes** (full per-subsystem detail on Emdash, produced in the same reading pass): [emdash-agents-and-architecture.md](./emdash-agents-and-architecture.md), [emdash-worktree-lifecycle.md](./emdash-worktree-lifecycle.md), [emdash-tracker-integrations.md](./emdash-tracker-integrations.md), [emdash-renderer-ui.md](./emdash-renderer-ui.md).

**The one-paragraph verdict:** vibe-kanban is the closest stack cousin (Rust + React) and the richest source of *negative* lessons — its DB-as-truth workspace model needed an orphan-reaping directory scanner, a background force-delete pipeline, and an env-var kill switch, and that machinery is exactly where its two reputation-damaging bugs live. Emdash is the richest source of *positive* mechanics — probe-then-derive lifecycle state, branch provenance recorded in git itself, plan/step teardown compiled from observed state — several of which independently arrive at reeve's own derive-don't-store thesis from inside an app whose primary store is SQLite. Sortie is the proof that the orchestration core can be tiny when truth lives outside the tool: four SQLite tables, plain directories, and a reconciliation loop against the tracker.

## 1. Skeleton — repo layout, boundaries, type contracts

### What they do

**vibe-kanban** is a Cargo workspace of ~30 crates (`vibe-kanban@Cargo.toml`). The ones that matter map cleanly onto reeve's rings: `db` (sqlx models + 60+ migrations), `services` (domain logic), `executors` (agent adapters), `git` (git2 + CLI wrapper), `worktree-manager` / `workspace-manager` (isolation lifecycle), `local-deployment` (process ownership, PTY), `server` (axum HTTP adapter), `utils`. The dependency rule is enforced *by crate boundaries only* — `git` cannot see `server` because it doesn't depend on it — there is no lint or CI check for layering beyond the crate graph. The rest of the workspace (11 `relay-*` crates, `remote`, `trusted-key-auth`) is the corpse of the cloud tier that killed the company; it is instructive to see how much surface the remote ambition added to a local tool.

**Type contract:** vibe-kanban generates `shared/types.ts` (887 lines) from Rust via **ts-rs**, through a dedicated binary that lists every exported type explicitly — ~100 `T::decl()` calls in `vibe-kanban@crates/server/src/bin/generate_types.rs` — wired as `npm run generate-types` and a `generate-types:check` drift gate (`vibe-kanban@package.json:35-36`). The generated file's header ends with *"If you are an AI, and you absolutely have to edit this file, please confirm with the user first."* — a sign of the times, and of the failure mode (agents patching generated output instead of the source).

**Emdash** is a pnpm + Nx monorepo: `apps/emdash-desktop` (Electron main + renderer), `apps/workspace-server` (remote/SSH worker), and packages `core` (domain mechanics), `plugins` (37 agent providers + 12 issue-tracker providers), `wire` (a homegrown typed RPC layer), `shared`, `ui`, `chat-ui`. Its boundary contract is **zod schemas at every seam**: the `wire` package defines six endpoint kinds — `procedure`, `liveState`, `liveLog`, `eventStream`, `liveJob`, `downloadFile` (`emdash@packages/wire/src/api/define.ts`) — and every main↔renderer interaction is a typed contract instance. This is the Electron-world equivalent of ts-rs, except the schema *is* the runtime validator.

**Sortie** is a single Go module: `cmd/sortie` plus ~20 `internal/` packages, standard library HTTP, a **716-line embedded `dashboard.html`** served via `go:embed` (`sortie@internal/server/dashboard.go:18`), and a dependency list you can read in one breath — fsnotify, prometheus, yaml, and `modernc.org/sqlite` (pure Go, no CGO) (`sortie@go.mod`). Adapters self-register from `init()` into a registry (`sortie@internal/tracker/file/file.go:26-28`, same pattern in `internal/agent/claude/claude.go`), and every adapter carries a compile-time interface check (`var _ domain.TrackerAdapter = (*FileAdapter)(nil)`). The single-binary claim is real: the whole product is the binary + one SQLite file + a YAML workflow file.

### For reeve

- **Adopt (vibe-kanban):** crate-per-ring. The crate graph *is* the dependency rule's first enforcement layer; reeve's greppable rule ("no `tauri::` outside adapters") is the second. vibe-kanban shows the first alone is almost enough — its `worktree-manager` compiles with no knowledge of axum or the DB. Keep reeve's `git`/`index`/`vault`/`pty`/`gh_client` as separate crates or at minimum separate modules with the grep rule in CI.
- **Adopt (vibe-kanban):** the ts-rs pattern *including* the explicit registration list and the `--check` CI mode. An explicit list is a feature, not a chore — the generated file's contents are reviewable as a diff, and nothing leaks into the frontend contract by accident.
- **Adopt (sortie):** compile-time interface satisfaction checks on every seam-trait implementation, and a degenerate in-memory/fixture implementation of each seam for tests (sortie's `file` tracker adapter is exactly reeve's "manual is the degenerate strategy" made testable).
- **Avoid (emdash):** six interaction patterns at the boundary. Emdash's `wire` is impressive machinery, but reeve's API doc deliberately fixed **two** patterns (request/response + process-attached stream); emdash demonstrates what the boundary grows into when each new feature is allowed to mint a new endpoint kind.
- **Avoid (vibe-kanban):** letting a speculative tier (remote/relay) metastasize through the workspace. Eleven crates of the final repo serve a product direction that killed the company.

## 2. Graph — storage of truth, SQLite patterns, context assembly

None of the three has a docs graph (the competitive-landscape finding stands); what the code teaches is *where each tool put truth* and what that cost them.

### What they do

**vibe-kanban: DB is truth.** Tasks, workspaces, sessions, and execution processes are SQLite rows; the filesystem worktree is a disposable materialization. A workspace row stores its worktree path as a string (`container_ref`), plus a `worktree_deleted` flag; worktrees **auto-expire** — a periodic job selects workspaces idle >72h (1h if archived) via a five-way SQL join over sessions and processes (`vibe-kanban@crates/db/src/models/workspace.rs:252-309`), deletes the directory, sets the flag, and recreates the worktree on demand when the task is next touched (`vibe-kanban@crates/local-deployment/src/container.rs:1276-1277`, clearing the flag). The idempotent recreate path (`ensure_worktree_exists`, §3) exists *because* the DB row and the directory can disagree. The migration folder is its own lesson: 60+ migrations, including a table (`execution_process_logs`) created in July 2025 and abandoned for flat files by 2026 (§4).

**Emdash: DB is truth, but JSON columns are versioned.** Drizzle ORM over better-sqlite3; the interesting invention is `versionedJsonColumn` — JSON blobs in columns validated by a zod schema with an explicit version-upgrade chain (`emdash@apps/emdash-desktop/src/main/db/schema.ts`, `emdash@apps/emdash-desktop/src/shared/core/linked-issue.ts`). The tables also read as an archaeology dig: `tasks.sourceBranch` "@deprecated — moved to workspaces.config", `tasks.workspaceProvider` "@deprecated — superseded by workspaces.type; still read in resolveBootstrap for legacy BYOI tasks", and so on — five deprecated columns still live in two tables. This is the routine cost of rows-as-truth under schema evolution; files-first tools pay a different (smaller) cost: front-matter conventions.

**Sortie: the tracker is truth.** Its entire SQLite schema is four operational tables — `retry_entries`, `run_history`, `session_metadata` (token counts), `aggregate_metrics` (`sortie@internal/persistence/sql/001_initial.sql`). Ticket state lives in GitHub/Linear/Jira labels and states; a reconciliation loop re-fetches running issues and reconverges local state against the remote, with the persistence interface deliberately narrowed to what reconciliation needs (`sortie@internal/orchestrator/reconcile.go:16-29`). Deleting sortie's DB loses retry timers and metrics — never work.

**Context assembly.** Emdash's nearest analogue to reeve's Context Package is `IssueDetail.context`: at link time, the issue plugin renders "everything the provider has on a single issue: the canonical fields plus provider-specific enrichment (comments, activity, linked docs) formatted as a markdown context string for agent prompts" (`emdash@packages/plugins/src/issues/types.ts:43-49`), stored as a snapshot with a `fetchedAt` timestamp. That is reeve's Materialized Region, independently invented — remote content is copied to a local snapshot *once*, and the agent reads the snapshot, not the API. Sortie's prompt layer is the deterministic-assembly benchmark: Go `text/template` in **strict mode** with a fixed data contract (`{issue, attempt, run}`) and a static analyzer that warns on unknown variables and fields *before any run* (`sortie@internal/prompt/prompt.go`, `sortie@internal/prompt/analyze.go`). No LLM anywhere in the retrieval path — ADR-0003's rule, shipped.

### For reeve

- **Adopt (sortie):** the four-table discipline. reeve's per-project `index.sqlite` should stay as small as sortie's DB — link index + run history, nothing that isn't derivable or operational. Sortie proves an orchestrator needs astonishingly little durable state of its own when truth lives elsewhere.
- **Adopt (emdash/sortie):** snapshot-at-import with a fetch timestamp (= Materialized Region) and strict-mode deterministic templating with pre-run static validation for the Context Package renderer. Sortie's template analyzer is the model for "the package preview can warn before launch."
- **Avoid (vibe-kanban):** the expiry machinery. Auto-expiring worktrees forced vibe-kanban to build recreation, flag-tracking, and a five-way SQL join to define "idle" — all to manage a cache of something git already knows. reeve's Workspace is 1:1:1 with a branch and lives until the user ends it; existence is a `git worktree list` query. No expiry, no flag, no recreation path.
- **Avoid (emdash):** rows-as-truth for work items. The deprecated-column graveyard is what a Ticket schema looks like after two years of SQLite migrations; reeve's equivalent churn lands in front-matter conventions on files the user can read and fix.

## 3. Workspaces — git module, worktree lifecycle, cleanup

This is the section ADR-0002 was written for. All the destructive-bug surface in vibe-kanban is here.

### vibe-kanban's git module: hybrid, with the CLI winning where it matters

The `git` crate uses **libgit2 (`git2`) for read/pure-ref operations and shells out to the git CLI for anything that mutates worktrees**. This is not incidental — it is documented in the code twice:

> "Use GitService to remove the worktree registration (force) if present. **The Git CLI is more robust than libgit2 for mutable worktree operations**" — `vibe-kanban@crates/worktree-manager/src/worktree_manager.rs:238-239`

> "**Prefer git CLI for worktree add to inherit sparse-checkout semantics**" — `vibe-kanban@crates/worktree-manager/src/worktree_manager.rs:315`

and once in the other direction: "base branch not checked out anywhere — use libgit2 pure ref operations" (`vibe-kanban@crates/git/src/lib.rs:641`). A Rust team that started with libgit2 ended up rebuilding the CLI path for every worktree mutation. reeve's ADR-0006 choice (system git only, `--porcelain`/`-z` contract) skips straight to where vibe-kanban converged, minus the dual dependency.

Worth copying regardless: **per-worktree-path creation locks** — a global map of path → async mutex so concurrent create/cleanup of the same worktree serialize (`worktree_manager.rs:16-17`, taken by both `ensure_worktree_exists`:96-105 and `cleanup_worktree`:407-416); **verify-after-create** (creation "reported success but path does not exist" is an error, :319-322); and **retry-once-after-metadata-cleanup** when `worktree add` fails on stale `.git/worktrees/<name>` metadata (:330-361).

The dark side of that last one: `force_cleanup_worktree_metadata` deletes `.git/worktrees/<name>` **with `remove_dir_all`, bypassing git entirely** (`worktree_manager.rs:368-388`). Reaching into another repo's `.git` internals with raw filesystem calls is the pattern behind the bug analysis below.

### How the vibe-kanban bugs happened

These two issues are cited in reeve's ADRs as motivating lessons. Here is the concrete code behind each.

#### The destructive-cleanup surface (issue #3406, "Git repository is wiped after deleting Vibe Kanban workspace")

There are **two independent destructive paths**, and both exist *because the DB is truth and the filesystem is a cache that must be reaped*.

**Path 1 — the orphan scanner.** On every startup (and the base-dir scan again after that), vibe-kanban walks the worktree base directory and, for **each subdirectory whose exact path string is not present in the DB**, recursively deletes it:

- Scan and check: `cleanup_orphans_in_directory` iterates `read_dir(workspace_base_dir)` and calls `DbWorkspace::container_ref_exists(&pool, &workspace_path_str)` — `vibe-kanban@crates/workspace-manager/src/workspace_manager.rs:557-610`.
- The check is raw SQL string equality: `SELECT EXISTS(SELECT 1 FROM workspaces WHERE container_ref = ?)` — `vibe-kanban@crates/db/src/models/workspace.rs:238-250`.
- On a miss: `cleanup_workspace_without_repos` → `remove_dir_all` on the whole directory — `workspace_manager.rs:612-649`.
- Trigger: spawned at startup in `spawn_workspace_cleanup`, followed by a 30-minute expiry loop — `vibe-kanban@crates/local-deployment/src/container.rs:299-325`.

Consequences of that design, all visible in the code: (a) **delete or reset the DB and every workspace directory — including uncommitted agent work — is destroyed at next startup**, because nothing on disk can prove it is legitimate; (b) the equality is *string* equality, so any path-normalization drift between what was stored and what `read_dir` returns (case, separators, symlinks, macOS `/private` aliases — which the *other* module carefully normalizes for its own comparisons, `worktree_manager.rs:189-221`, but this check does not) marks a live workspace as orphaned; (c) if the user pointed the configurable workspace directory at a folder containing anything else, the scanner would reap it. The team knew all three: the base-dir override now force-appends an app-owned subdirectory with the comment *"Always use app-owned subdirectory within custom path for safety. **This ensures orphan cleanup never touches user's existing folders**"* (`worktree_manager.rs:512-517`), and there is a `DISABLE_WORKTREE_CLEANUP` env-var kill switch (`workspace_manager.rs:539-544`). A safety subdirectory and a kill switch are the fingerprints of a scanner that has already eaten user data.

**Path 2 — workspace deletion.** Deleting a workspace with "delete branch" checked runs, **in a detached background task after the HTTP handler has already returned 202** (`vibe-kanban@crates/server/src/routes/workspaces/core.rs:180-182`): force worktree removal (`git worktree remove --force`), raw `remove_dir_all` of the worktree *and* of `.git/worktrees/<name>` metadata inside the main repo, `git branch -D` (force) per repo, and `git worktree prune` (`workspace_manager.rs:217-267` → `worktree_manager.rs:230-265` → `crates/git/src/cli.rs:419-423`). No lock is held on the main repository; nothing coordinates with other git clients.

Issue #3406 reports `.git/objects` "mostly cleared out" after exactly this operation, with GitKraken open on the same repo and other live vibe-kanban worktrees ([BloopAI/vibe-kanban#3406](https://github.com/BloopAI/vibe-kanban/issues/3406) — reporter's own account; never root-caused by maintainers before the shutdown). The code facts above support a concrete mechanism, which should be read as *plausible, not confirmed*: the deletion pipeline force-deletes branches (making their commits unreachable) and mutates `.git` internals with raw filesystem calls, unlocked, concurrently with any other tool's `git gc --auto`. Git's garbage collector computes reachability from refs plus each registered worktree's HEAD/index metadata under `.git/worktrees/`; a gc that runs while that metadata is being deleted out from under it, in a repo whose refs are mid-mutation, can prune objects that live worktrees still need. Whatever the exact interleaving was, the *class* of bug is certain: **a multi-step, force-flagged, fire-and-forget destroy sequence that edits another repo's `.git` directly and holds no lock is not a safe operation on a repository the user shares with other tools.**

**What reeve's design already does about it, now with evidence:** the workspace registry is *derived from git* (branch name encodes the ticket; existence is `git worktree list`), so there is no DB row to desync from disk, no orphan concept, no scanner, and nothing to reap — a manually deleted worktree simply stops appearing in queries (ADR-0006). Discard is a foreground, awaited, per-workspace operation (kill → delete with retries → `prune` → verify), not a startup sweep. The one rule this section adds to the LLD: **reeve must never delete anything it cannot first prove it created** — see emdash's provenance pattern below — and must never touch `.git` internals with filesystem calls.

#### The state-reset failure (issue #3434, "deleting db.v2.sqlite does not reset auth state")

The user's expectation was reeve's own recovery model: *delete the database, get a clean slate*. It failed for two reasons visible in the report ([BloopAI/vibe-kanban#3434](https://github.com/BloopAI/vibe-kanban/issues/3434)): (1) **state was scattered** — alongside `db.v2.sqlite` the data dir holds `config.json`, `profiles.json`, a `server_ed25519_signing_key`, and a `sessions/` directory, so deleting the DB deleted only one of five stores and the app "still bypasses the login screen entirely"; (2) the login flow depended on a **remote endpoint** (`api.vibekanban.com/api/auth/methods`) that by then resolved to a domain-parking page, so the auth UI silently failed regardless. The lesson is double: "delete the DB" is only a real recovery path if *every* piece of session/derived state lives in (or is invalidated with) the DB, and no local-first startup path may block on a network endpoint. reeve's version: exactly one deletable derived store per project (`index.sqlite`), config in human-readable JSON that *is* truth (not cache), no accounts, no remote calls at startup (NFR-5's "nothing local ever waits on the network").

### Emdash's lifecycle: the best mechanics in the field

Emdash models workspace setup/teardown as **intent → compiled plan → typed steps → runner**:

- An intent (`use-branch`, `create-branch`, `clone-repository`, `plain-directory`, PR checkout) compiles to an ordered list of declarative steps — `add-worktree`, `create-local-branch`, `set-branch-base`, `copy-preserved-files`, etc. (`emdash@packages/core/src/workspace-lifecycle/plan/planner.ts`).
- A **probe** inspects reality — is the directory there, is the worktree registered (`git worktree list --porcelain`), does the branch exist — into an `ObservedWorkspaceState`, and the lifecycle *phase* is **derived from the probe**, not read from a stored status column: `derivePhase(observed, inFlight)` (`emdash@packages/core/src/workspace-lifecycle/probe.ts:33-42`). This is reeve's derive-don't-store board rule, implemented inside an Electron/SQLite app because stored status kept lying.
- **Teardown is compiled from the probe, not from a remembered plan** (`compileTeardownFromProbe`, `emdash@packages/core/src/workspace-lifecycle/plan/teardown.ts`): only remove the worktree if it is actually registered or the directory exists, and — the key line — **only delete the branch if `observed.branchCreatedByEmdash`** (`teardown.ts:58-64`).
- Branch provenance is recorded **in git config, not the DB**: creating a branch sets `branch.<name>.emdash-created = true`, and the probe reads it back with `git config --bool --get` (`probe.ts:124-137`). Emdash also records each branch's base ref as `branch.<name>.base` (`emdash@apps/emdash-desktop/src/main/core/projects/worktrees/worktree-service.ts:200-220`). Metadata about git state stored *in git* survives DB loss, travels with the repo, and is inspectable with stock tooling.
- The step runner classifies failures and **retries only `transient` ones** on a delay schedule (`emdash@packages/core/src/workspace-lifecycle/runner/runner.ts:114-116`) — the disciplined version of "delete with retries" that reeve's Windows-safe destroy needs.

Two caveats to copy around, not through: the `remove-worktree` step falls back from `git worktree remove --force` to a blind `rm -rf` and **reports success either way** (`emdash@packages/core/src/workspace-lifecycle/steps/impl/remove-worktree.ts`) — reeve's discard must verify and report, not swallow. And emdash keeps its worktree pool *inside* the repo under `.emdash/`, hidden via `.git/info/exclude` rather than `.gitignore` (`emdash@apps/emdash-desktop/src/main/core/projects/ensure-emdash-excluded.ts`) — the exclude-file trick is elegant (no dirty `.gitignore`), but in-repo worktrees deepen Windows paths and put agent blast radius next to the user's checkout; reeve's `~/.reeve/worktrees/<slug>/` placement stands.

### Sortie: no worktrees at all

Sortie's workspace is a plain directory (`Ensure(root, identifier)`) plus user-configured `after_create` / `before_run` hook scripts that receive `SORTIE_*` env vars; git arrangement is entirely the hooks' business (`sortie@internal/workspace/lifecycle.go`). One detail worth stealing: **transactional rollback on setup failure** — if `after_create` fails on a *newly created* workspace, the directory is removed so the retry starts clean, but a `before_run` failure preserves the directory because it may hold prior agent work (documented failure semantics in `lifecycle.go:83-96`). Discriminating "safe to destroy because I just made it and it's empty of value" from "may contain work" is precisely the distinction vibe-kanban's cleanup paths lack.

## 4. Runs — spawn model, run registry, logs

### Spawn model: two coherent philosophies, one fragile hybrid

**vibe-kanban: no PTY for agents.** Every agent executor spawns the CLI with **piped stdio** — `Stdio::piped()` on all three streams (`vibe-kanban@crates/executors/src/executors/claude.rs:633-635`) — speaking each agent's headless JSON protocol (`--input-format=stream-json --output-format=stream-json` for Claude, `claude.rs:190-191`; Codex/ACP/etc. each have their own module under `executors/src/executors/`). Processes are spawned into a **process group** (`group_spawn_no_window()`, `claude.rs:650` — also the Windows no-console trick), and cleanup SIGKILLs "any orphaned children (e.g. MCP servers) still in the process group" after the executor exits (`vibe-kanban@crates/local-deployment/src/container.rs:804-807`). PTY exists in the codebase, but **only** for the user-facing interactive terminal — a `PtyService` on `portable-pty` bridged to xterm over WebSocket (`vibe-kanban@crates/local-deployment/src/pty.rs`, `crates/server/src/routes/terminal.rs`). The cost of the piped model is a **per-agent protocol adapter forever**: the `executors` crate is thousands of lines of normalization per vendor, exactly the "deep per-agent integration" reeve ruled out in [agent-invocation.md](./agent-invocation.md).

**Emdash: PTY-first, with a completion-detection workaround worth studying.** Agents run in real PTYs (`node-pty`), and prompt delivery is a **declared per-agent capability** with four kinds: `argv`, `keystroke`, `stdin-pipe`, `none` (`emdash@packages/core/src/agents/plugins/capabilities/prompt.ts`). The `keystroke` kind is the fragile one, and emdash's own code documents why: injection waits for the TUI to produce output *and then go quiet for 800ms* (max 15s) before typing, because — their comment — *"fixed delays race the agent's startup (auth, sync, model load)"* (`emdash@apps/emdash-desktop/src/main/core/conversations/impl/keystroke-injection.ts:8-10`). Completion detection is cleverer: for agents with hook systems (Claude Code's start/notification/stop hooks), emdash **injects a hook configuration that makes the agent itself call home** — a `curl`/PowerShell one-liner POSTing to a localhost HTTP server with a per-session nonce token and PTY id in headers (`emdash@packages/core/src/agents/plugins/helpers/hooks.ts`, server in `emdash@apps/emdash-desktop/src/main/core/agent-hooks/hook-server.ts`). No terminal-output parsing; the agent announces its own lifecycle. Session identity is likewise a per-agent capability (emdash's conversation UUID passed as `claude --session-id`, or the provider's own session id captured for resume — `capabilities/prompt.ts:9-16`).

**Sortie: headless turn loop.** Each adapter runs the agent CLI as a subprocess in headless mode, reads newline-delimited JSON from stdout, and normalizes to domain events; `RunTurn` is the unit (`sortie@internal/agent/claude/claude.go:1-6`). No PTY, no UI, retry with exponential backoff and stall detection driven from the orchestrator (`sortie@internal/orchestrator/reconcile.go:52-58`).

**For reeve:** the three models triangulate reeve's choice well. reeve's v1 is PTY-passthrough with the Context Package doing prompt delivery via `AGENTS.md` + argv — which sidesteps *both* costs: no per-agent JSON protocol zoo (vibe-kanban's tax) and no keystroke injection races (emdash's tax). Two mechanics to lift anyway: vibe-kanban's **process-group spawn + group kill** (reeve's "reeve owns its children" needs the group, or agents' MCP-server children survive the kill), and emdash's **hook-callback trick** as a post-v1 option for richer completion signals on agents that support hooks — it is agent-agnostic in spirit (the hook config is data, not a protocol adapter).

### Run registry

vibe-kanban holds live children in an in-memory map guarded per execution (`child_store`, `container.rs:801-810`), with rows in `execution_processes` for history — the same split as reeve's in-memory run registry + SQLite run history. Emdash's PTY registry is per-task in the renderer (§6). Sortie's is the orchestrator's slot table with a `session_metadata` row per issue. Nothing here contradicts reeve's design; vibe-kanban's startup also reconciles crashed runs by marking rows with no live process, as reeve plans.

### Logs: the DB-to-files migration vibe-kanban paid for

vibe-kanban's execution logs started as **DB rows** (`execution_process_logs` table, created `vibe-kanban@crates/db/migrations/20250729162941_create_execution_process_logs.sql`) and ended as **JSONL files** (`sessions/<session>/processes/<process>.jsonl` under the app data dir, `vibe-kanban@crates/utils/src/execution_logs.rs`). The transition required a one-time startup migration that streams every process's rows out to files with a progress bar, then `delete_all` + `VACUUM` (`vibe-kanban@crates/services/src/services/execution_process.rs:60-180`). High-volume append-only output in SQLite bloated the DB enough to justify writing an in-product ETL with a TTY progress UI. reeve's HLD already puts raw PTY logs in plain files under `~/.reeve/projects/<slug>/logs/` from day one — this migration is the receipt for that decision.

### Event streaming: the derived-event machine to avoid

vibe-kanban streams live state to the UI by installing **SQLite `preupdate`/`update` hooks on the connection**: every row change fires a hook, which (for updates/inserts) spawns an async task to **re-fetch the row by rowid** and emit a JSON-patch into a `MsgStore`, delivered to the frontend over SSE and applied client-side with rfc6902 (`vibe-kanban@crates/services/src/services/events.rs:59-200`, `crates/server/src/routes/events.rs`, `crates/utils/src/msg_store.rs:70-71`). The complexity is visible in the fallbacks: the re-fetch can find the row already gone (`DeletedWorkspace { rowid }` variants), deletes need the *pre*-update hook because post-hoc fetch would miss, and the scratch table needs composite-key special-casing. This is what "the DB is truth, so the DB must also be the event source" costs. reeve's model — coarse scope-carrying invalidation events (`graph_changed { paths }`) from the file watcher, UI re-queries — never diffs rows, never patches JSON, and has exactly one emission path.

## 5. Sources — tracker abstractions, gh clients, stored vs derived

### What they do

**Emdash** has the cleanest source seam. Issues are a **plugin capability** over a provider-neutral shape — `IssueData { identifier, title, url?, description?, branchName?, status?, assignees?, ... }` (`emdash@packages/plugins/src/issues/types.ts`) — with the host normalizing inputs *before* the plugin sees them (limits clamped, search terms trimmed, empty searches short-circuited — `types.ts:21-26`). A provider implementation is small: GitHub's is two functions over octokit plus a mapper (`emdash@packages/plugins/src/issues/impl/github/index.ts`). **Stored vs derived is sharply drawn:** the only thing persisted is the `linkedIssue` snapshot on the task (identifier, title, url, status, the rendered markdown `context`, `fetchedAt` — `emdash@apps/emdash-desktop/src/shared/core/linked-issue.ts`); issue lists and details are always live queries, cached only by the query layer. Twelve providers (GitHub, Linear, Jira, GitLab, Plane, Asana, Monday, Notion, Trello, Forgejo, Featurebase, Plain) sit behind the one shape — empirical proof that reeve's agnostic `list_source_items` DTO can survive real provider diversity.

**vibe-kanban** ships a `git-host` crate whose GitHub support **shells out to the `gh` CLI** — resolving the binary from PATH, running `gh repo view` / `gh pr create`, and detecting auth failures first by `gh`'s documented exit code 4, then by string-matching stderr for older versions (`vibe-kanban@crates/git-host/src/github/cli.rs:154-184`). This is reeve's `gh_client` seam already in production Rust, including the sharp edge (CLI output/exit-code contracts drift across `gh` versions; pin a minimum in preflight).

**Sortie** talks to `api.github.com` directly (REST + GraphQL) through its own thin `httpkit` client with an **ETag cache** to survive rate limits (`sortie@internal/scm/github/etag_cache.go`, endpoint default at `ci.go:93`). Its tracker seam is the most complete state-machine treatment: seven-operation `TrackerAdapter` interface, configurable active/terminal/handoff states, and the reconciliation loop that treats the remote tracker as authoritative (`sortie@internal/orchestrator/reconcile.go:34-50`). It also ships a `file` tracker adapter — a JSON fixture on disk implementing the full interface, with in-memory transition overrides, "intended for development and testing where a live tracker API is unavailable" (`sortie@internal/tracker/file/file.go:1-8`).

### For reeve

- **Adopt (emdash):** host-side input normalization *before* the strategy is invoked (the seam's callers should never depend on each strategy clamping its own limits), and the snapshot-with-`fetchedAt` rule for what gets stored. Emdash's twelve-provider registry also confirms reeve's "adding Linear changes zero API operations" claim is realistic.
- **Adopt (sortie):** the fixture-file `TicketSource` implementation as reeve's test double — it slots exactly where reeve's degenerate `manual` strategy already lives, and it makes source-service tests hermetic.
- **Adopt (vibe-kanban):** the `gh` CLI wrapper shape, including exit-code-first error classification with string fallback. Budget for `gh` version drift in preflight (FR-4.4).
- **Avoid (sortie, for reeve's model):** remote-as-truth reconciliation. It is *correct for sortie* (an autonomous daemon whose board IS the tracker) and wrong for reeve, where the local file is truth and refresh is a curated, user-initiated act. The two positions are both coherent; mixing them (local edits + background remote reconciliation) is where conflicts would breed.

## 6. Frontend — surfaces, state, terminal, diff

### What they do

**vibe-kanban** (`packages/local-web`, shared logic in `web-core`): TanStack Query + TanStack Router, zustand for UI state, **TanStack DB collections fed by SSE JSON-patches** (rfc6902 applied client-side) for live data, xterm 5 with fit/web-links addons, virtualized lists (`vibe-kanban@packages/local-web/package.json:52-97`). The event-patch plumbing on the client is the mirror of the server-side hook machine (§4) — two nontrivial codebases exist to keep row-level live state in sync, versus reeve's re-query-on-invalidate.

**Emdash** organizes the renderer by **feature folders** (`renderer/features/{tasks,conversations,projects,sidebar,command-palette,...}`) and mixes **MobX** class stores (observable maps, `observer` components) with TanStack Query for fetched data. Three mechanics matter for reeve:

- **Terminal registry:** PTY-backed terminal stores live in a MobX map keyed by task id, acquired/released by mount-count — the store (and thus the xterm buffer and PTY) **outlives the React component**, so switching tabs never kills or clears a terminal (`emdash@apps/emdash-desktop/src/renderer/features/tasks/stores/terminal-registry.ts`). On the main side, `PtySession` appends all output into a replayable `LiveLog` buffer, so a re-attached view can restore scrollback (`emdash@packages/core/src/pty/pty-session.ts:25-36`). reeve's Workspace surface needs exactly this: registry keyed by ticket id, buffer ownership outside the component tree.
- **Diff viewer:** Monaco's diff editor with a model registry, prefetching of file models, and **inline comments attached to diff lines** that feed back into the agent conversation (`emdash@apps/emdash-desktop/src/renderer/features/tasks/diff-view/`, comments in `diff-view/comments/use-diff-editor-comments.ts`). Monaco is heavy but brings language coloring and the comment-anchoring machinery for free; the competitive-landscape doc already flagged inline-comments-to-agent as the field's best review primitive — this is its implementation.
- **No board.** Emdash renders tasks as a sidebar/list with status chips, not a kanban; vibe-kanban has the real board. reeve's four-fixed-columns board has no code model to copy in emdash; vibe-kanban's board is a straightforward column render over status enums (the interesting part — derivation — is server-side).

**Sortie**'s "frontend" is one embedded 716-line HTML dashboard with inline JS polling JSON endpoints (`sortie@internal/server/dashboard.html`) — the existence proof that an orchestrator's monitoring UI can be one file when the tool's real UI is the tracker itself.

### For reeve

- **Adopt (emdash):** the terminal-registry pattern (buffer + session ownership outside React, keyed by ticket) and Monaco's diff editor as the LLD's diff-viewer candidate to evaluate first — it is the only OSS implementation in this cohort with working inline diff comments.
- **Adopt (both):** TanStack Query as the query-cache layer. Both apps use it as the fetch/invalidation backbone; reeve's "thin query cache keyed by operation + args, invalidated by scoped events" is a textbook TanStack Query setup (`invalidateQueries` on `graph_changed.paths` prefixes). This effectively settles the HLD's deferred state-library question in Query's favor for server state, with anything zustand/MobX-shaped reserved for pure UI state only.
- **Avoid (vibe-kanban):** client-side JSON-patch state mirroring. It exists to serve the server's row-level event stream; reeve's coarse invalidation makes the entire patch pipeline (rfc6902, collections, patch-ordering concerns) unnecessary.
- **Avoid (emdash):** two overlapping reactive systems. MobX stores + TanStack Query + wire liveModels in one renderer means three sources of truth for "current state of task X"; emdash needed a `reset-stale-acp-agent-statuses.ts` (the name says it) to reconcile them. One query cache + one UI-state store is the ceiling.

## 7. Top 10 takeaways for reeve's LLD

1. **The derive-don't-store bet is confirmed by the failure it prevents.** vibe-kanban's DB-as-truth workspace model *requires* an orphan scanner that deletes any directory the DB doesn't recognize (`workspace_manager.rs:557-610`) — which turns DB loss, path drift, or a misconfigured base dir into data destruction, acknowledged in-code by a safety subdirectory and a `DISABLE_WORKTREE_CLEANUP` kill switch. reeve's git-derived registry has no orphan concept; there is nothing to reap.
2. **Never delete what you can't prove you created.** Emdash records `branch.<name>.emdash-created = true` in git config and teardown checks it before deleting a branch (`probe.ts:124-137`, `teardown.ts:58-64`). reeve should mark its branches/worktrees the same way (git config or a marker file under the managed root) and make discard refuse anything unmarked.
3. **Worktree teardown is a safety-critical, foreground, locked operation.** vibe-kanban's deletion is a fire-and-forget background task that force-removes worktrees, raw-deletes `.git/worktrees/` metadata, and force-deletes branches with no repo lock — the surface under the repo-wipe report (#3406). reeve's discard: awaited command, per-workspace lock, git-mediated operations only (never `remove_dir_all` inside `.git`), verify at the end.
4. **"Delete the DB" is only a recovery path if it's the *only* mutable store.** #3434's real mechanism: auth state scattered across five files plus a dead remote endpoint in the startup path. reeve: one deletable `index.sqlite` per project, truth in files/JSON, zero network at startup.
5. **Shell out to git; don't embed it.** The Rust team that had libgit2 wrote, in code comments, that the CLI is more robust for every mutable worktree operation and better for sparse-checkout semantics (`worktree_manager.rs:238-239, 315`). ADR-0006's system-git decision skips that whole detour. Keep vibe-kanban's per-path creation locks, verify-after-create, and one-retry-after-cleanup.
6. **Raw run logs are files from day one.** vibe-kanban shipped an in-app ETL with a progress bar to move logs out of SQLite into JSONL (`execution_process.rs:60-180`) — the receipt for reeve's `~/.reeve/.../logs/` plan.
7. **Coarse invalidation beats row-level event streaming.** vibe-kanban needed SQLite preupdate/update hooks, rowid re-fetch races, JSON-patch generation, SSE, and a client patch-application layer to keep the UI live. reeve's `graph_changed { paths }` + re-query eliminates both codebases. The PTY stream stays the single push exception.
8. **PTY passthrough dodges both integration taxes.** vibe-kanban pays a permanent per-agent stream-JSON adapter zoo; emdash pays keystroke-injection races ("fixed delays race the agent's startup") and per-agent capability matrices. reeve's argv + `AGENTS.md` delivery avoids both. Spawn agents in a **process group** and group-kill (vibe-kanban, `container.rs:804-807`), or MCP children survive. Post-v1, emdash's agent-hook-to-localhost callback (`hook-server.ts`) is the richest agnostic completion signal available.
9. **The sources seam is proven at scale — keep DTOs neutral and normalize inputs in the host.** Emdash runs 12 trackers behind one `IssueData` shape with host-side normalization; snapshot-with-`fetchedAt` matches the Materialized Region. Copy sortie's file-fixture adapter as the test double, and vibe-kanban's `gh` CLI wrapper (exit-code-4 auth detection) for `gh_client`.
10. **Frontend: TanStack Query + a terminal registry + Monaco diff, and nothing cleverer.** Both React apps converge on TanStack Query; emdash's task-keyed terminal registry (PTY and buffer owned outside React, `terminal-registry.ts`) and Monaco diff-with-inline-comments are the two components worth lifting near-verbatim. Skip client JSON-patch mirroring and skip running two reactive state systems side by side.
